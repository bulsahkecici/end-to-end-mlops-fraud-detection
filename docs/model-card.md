# Model card: `ieee_fraud_lgbm`

## Purpose

Estimates the probability that a credit-card transaction is fraudulent, to
support (not replace) a human/automated fraud-review workflow. Output is a
calibrated-effort probability plus a thresholded binary decision — it is
**not** a legal or final determination that a transaction is fraudulent.

## Data

- Dataset: [IEEE-CIS Fraud Detection](https://www.kaggle.com/c/ieee-fraud-detection/data) (Vesta Corporation / IEEE-CIS), a public Kaggle competition dataset of anonymized e-commerce transactions.
- Target: `isFraud` (binary; ~3.5% positive rate in the full real dataset).
- Features actually used: numeric transaction/behavioral features
  (`TransactionAmt`, `C*`, `D*`, `V*`, etc.) and categorical features
  (`ProductCD`, `card4`, `card6`, `P_emaildomain`, `M*`, etc.), selected
  automatically per training run by dtype (`src/features/pipeline.infer_schema`)
  from whatever raw transaction+identity columns are present — this is not
  a hand-curated feature list, and will differ slightly between a run on
  the real Kaggle data (434 raw columns) and a run on the small synthetic
  fixture (~13 columns).

## Modeling approach

- One `sklearn.Pipeline`: `ColumnAligner` → `ColumnTransformer` (median
  imputation for numeric, most-frequent + ordinal-encoding for categorical)
  → `LGBMClassifier`.
- Categorical encoding is ordinal (integer-coded), not LightGBM's native
  categorical splits or one-hot — a deliberate simplification chosen for
  train/serve parity robustness against arbitrary/loosely-typed JSON input,
  at some cost to split quality on very high-cardinality columns. Native
  categorical handling or target encoding is a reasonable future
  improvement (see "Known limitations").

## Validation strategy

- **Temporal split** (default): earliest ~70% of transactions (by
  `TransactionDT`) → train, next ~15% → validation, final ~15% → test.
  Chosen because fraud behavior and the underlying feature distributions
  drift over time — a random split would let the model implicitly "see the
  future" during training and overstate real-world performance.
- Random stratified split is available (`SPLIT_STRATEGY=random`) as an
  explicit smoke-test fallback only.
- All preprocessing (imputation statistics, categorical encoding) is fit on
  the train split only; validation/test only ever go through `.transform()`.
- The **test** split is used exactly once, for final reporting — never for
  threshold selection or model comparison, both of which use validation.

## Metrics (synthetic smoke-training example)

Exact numbers vary by dataset/seed/sample size; a representative run on
6,000 synthetic rows (`python -m src.modeling.train --data-source
synthetic --n-synthetic 6000`) logs, per split, to MLflow:
`roc_auc`, `pr_auc`, `precision`, `recall`, `f1`, `log_loss`,
`brier_score`, `fraud_rate`, and the confusion matrix. See
`reports/model_comparison.md` (generated by `src/registry/compare.py`)
for the latest candidate-vs-champion comparison.

## Threshold

Selected on the **validation** set via one of four configurable strategies
(`THRESHOLD_STRATEGY` env var): `best_f1` (default), `target_recall`,
`cost_based` (uses `FALSE_NEGATIVE_COST` / `FALSE_POSITIVE_COST`), or
`fixed`. The selected threshold is logged as an MLflow param and embedded
in the model's metadata artifact, so `/predict` always reports the
threshold that was actually used to produce `fraud_prediction` — never a
silently hardcoded `0.5`.

## Known limitations

- Categorical encoding is ordinal rather than native/target-encoded (see
  above) — may under-perform on very high-cardinality columns
  (`DeviceInfo`, `id_30`/`id_31`) relative to a more sophisticated encoder.
- The default synthetic data generator (`make_synthetic_transactions`) is a
  simplified, hand-authored risk signal for testing/CI — it is **not**
  representative of real fraud patterns and models trained on it should
  never be used for anything beyond pipeline validation.
- No fairness/subgroup analysis has been performed (the dataset does not
  expose demographic attributes suitable for one).
- The promotion gate compares against the current champion's *logged
  metrics*, not a fresh side-by-side scoring run — if the champion and
  candidate were evaluated on different validation windows (e.g. after a
  resampling-strategy change), the comparison is directionally useful but
  not a strictly controlled A/B test.

## Bias and ethical considerations

- False positives (flagging a legitimate transaction as fraud) have a
  direct customer-experience/trust cost; false negatives have a direct
  financial-loss cost. The cost-based threshold strategy exists precisely
  to make this trade-off explicit and configurable rather than implicit in
  a hardcoded 0.5 cutoff.
- The model should not be the sole basis for denying a transaction or
  taking action against a customer — treat `fraud_prediction` as a
  prioritization signal for human/automated review, not a final verdict.

## Do not use for

- Any decision with legal, credit, or civil-rights implications made
  without human review.
- Any dataset/domain other than the transaction schema it was trained on
  (e.g. do not repurpose this model for a different payment product
  without retraining).
- Production traffic if trained only on the synthetic fixture — that data
  has no real predictive signal for actual fraud.

## Retraining triggers

- `src/monitoring/drift.py` reports a shift on `TransactionAmt` or any
  categorical column beyond its configured threshold.
- A material change in the upstream data schema or sampling strategy.
- A scheduled cadence appropriate to the deployment (not automated in this
  project — retraining is triggered manually via `make train-ieee`, then
  gated through `make promote` before it can affect production traffic).
